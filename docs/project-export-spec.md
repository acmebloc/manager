# 프로젝트 콘텐츠 다운로드(내보내기) 기능 명세

**구현 완료, 로컬 검증 완료 (2026-09-02), 커밋 전.** 프로젝트 상세페이지
(`ProjectDetailPage.jsx`)에서 일감/일정을 파일로 내려받는 기능 — 같은 페이지에 이미
있는 엑셀 일괄 업로드(`TaskExcelImport.jsx`/`taskImport.js`, `docs`엔 별도 스펙 없이
메모리로만 기록됨)와 대칭되는 내보내기 기능이다.

기존 코드베이스에는 내보내기/다운로드 기능이 전혀 없었다(작업 첨부파일 원본을 그대로
스트리밍하는 `taskAttachments.js`의 다운로드 라우트만 유일한 선례). CSV/HTML용
라이브러리도 없었고, exceljs는 그때까지 **읽기(import)** 용도로만 검증돼 있었다 —
쓰기(`workbook.xlsx.writeBuffer()`)는 이 기능에서 처음 쓴 경로이며, 로컬에서 왕복
읽기 검증까지 마쳤다.

**구현 파일**: `server/src/routes/projectExport.js`(라우트), `server/src/lib/projectExport.js`
(데이터 로딩+행 변환), `server/src/lib/exportFormats.js`(CSV/HTML/xlsx 렌더러),
`src/components/ProjectExportMenu.jsx`(프론트 UI). 상세는 각 섹션 참고.

## 1. 다운로드 스코프 & 파일 구성

| 스코프 | 내용 |
| --- | --- |
| 전체 | 일감 + 일정 |
| 일감만 | Task |
| 일정만 | Schedule("기타"+반복) + 화면(간트차트)에 막대로 같이 뜨는 일감 — §3 참고 |

**변경 이력**: "일정만" 스코프는 처음엔 순수 Schedule 테이블만으로 정했었으나(간트차트의
"일감" 막대는 Task에서 매 요청마다 계산되는 표시용 값이라는 이유), 실제 화면을 보고
사용자가 "일정표에 등록된 상태면 일감도 일정으로 봐야 하지 않냐"고 재확인해 **화면과
동일한 범위로 확정**했다(2026-09-02). 아래 §3이 최신 기준이다.

포맷: **CSV, Excel(xlsx), HTML, JSON**.

**파일 결합 규칙 (확정)**: 어떤 포맷이든 일감과 일정은 **항상 별도 파일**로 만든다.
"전체" 선택 시 두 파일을 **zip**으로 묶어 제공한다. Excel도 시트 2개짜리 워크북 하나가
아니라 `tasks.xlsx` + `schedules.xlsx` 두 파일을 zip으로 묶는다.

다운로드 버튼은 **프로젝트 참여자 전원**에게 노출한다 (조회 권한과 동일하게
`requireProjectRole('member')` 기준 — 엑셀 업로드처럼 PM 전용이 아니다). PM 여부는
어느 필드에도 별도 표기하지 않는다.

## 2. 일감(Task) 필드

| 컬럼 | 소스 | 비고 |
| --- | --- | --- |
| 프로젝트명 | `Project.name` | |
| 제목 | `Task.title` | |
| 작성자 | `Task.createdBy` | 닉네임(`User.name`)+이메일 |
| 담당자 | `Task.assignee` | 닉네임+이메일, 작성자와 동일 형식 |
| 시작일 | `Task.startAt` | 없으면 빈칸 (간트차트용 등록일 대체 표시는 순수 화면용이라 여기서 안 씀) |
| 종료일 | `Task.endAt` | 없으면 빈칸 |
| 진행상태 | `Task.status` | 화면에 쓰는 한글 라벨 그대로(등록/진행/검수/완료) |
| 유형 | `Task.type` | 화면 라벨 그대로(기획/개발/디자인/QA) |
| 등급 | `Task.grade` | 화면 라벨 그대로 |
| 첨부파일유무 | `_count.attachments > 0 ? 'O' : 'X'` | 실제 파일은 내려주지 않음 |

**명시적으로 제외**: `description`(마크다운 본문, 이미지 base64 임베드 가능 — 기존
목록 API도 같은 이유로 이미 제외 중), `TaskComment`(댓글, 개수도 미표시), 첨부파일
실물, `TaskLink`(일감 간 관계).

## 3. 일정(Schedule) 필드

일반 일정, 반복 일정, 화면(간트차트)에 막대로 같이 뜨는 일감을 표 하나로 합친다 —
일감 유래 행과 진짜 일정 유래 행을 구분하는 컬럼은 두지 않는다(2026-09-02 확정,
사용자 표현: "일정을 다운받은 거니까 그냥 다 일정으로 인식시키는 게 좋다"). 컬럼:

| 컬럼 | 소스 | 비고 |
| --- | --- | --- |
| 프로젝트명 | `Schedule.project.name` / `Project.name` | |
| 제목 | `Schedule.title` / `Task.title` | |
| 시작일 | 아래 "반복일정 계산 규칙" 참고 / `Task.startAt` | |
| 종료일 | 아래 "반복일정 계산 규칙" 참고 / `Task.endAt` | |
| 담당자 | `Schedule.owner` / `Task.assignee` | 닉네임+이메일, 없으면 빈칸 |
| 참조자 | `ScheduleFollower[]` / (일감 유래 행은 항상 빈칸 — 대응 개념 없음) | 여러 명이면 **한 셀에 콤마로 구분**(CSV/Excel/HTML). **JSON은 배열**로 유지 |
| 반복여부 | `recurrenceIntervalWeeks` 존재 여부 | **O만 표시, 비반복은 빈칸**(X 아님 — 일감 유래 행이 전부 비반복이라 X로 채우면 칸이 온통 X로 뒤덮이는 걸 피하려고 2026-09-02에 X→빈칸으로 변경) |

### 3.1 "일정" 스코프에 포함되는 일감 (2026-09-02 확정)

화면의 "일정" 페이지(간트차트)는 실제 `Schedule` 레코드("기타"/"반복 일정")뿐 아니라
**시작일 또는 종료일이 있는 일감도 막대로 같이 보여준다** — 사용자가 이 화면을 보고
"화면에 등록된 상태면 일정으로 봐야 한다"고 판단해, 다운로드도 이 범위를 그대로
따르기로 확정했다. 단:

- **시작일/종료일이 둘 다 없는 일감은 제외한다.** 화면은 이런 일감을 등록일
  (`createdAt`) 기준 1일짜리 회색 막대로 "표시만" 해주는데(순수 화면용 placeholder,
  `Task`에는 그 날짜가 저장되지 않음 — `src/lib/ganttDates.js`), 이 값을 진짜 시작일인
  것처럼 파일에 쓰면 존재하지 않는 데이터를 만들어내는 셈이라 제외한다. 이 일감은
  "일감" 다운로드에 이미 (빈 날짜로) 포함돼 있어 정보 손실은 없다.
- 일감 유래 행은 반복 대상이 아니므로 반복여부는 항상 빈칸.
- "전체" 다운로드 시 시작일/종료일이 있는 일감은 "일감" 파일과 "일정" 파일 양쪽에
  다른 컬럼 형태로 각각 나타난다(중복이 아니라 서로 다른 관점 — 의도된 동작).

### 3.2 반복일정 시작일/종료일 계산 규칙 (확정)

반복일정은 DB에 규칙(`recurrenceIntervalWeeks`/`recurrenceEndAt`)만 저장되고, 화면
조회 시 매번 `server/src/lib/scheduleRecurrence.js`의 `expandOccurrences()`로 회차를
계산한다. 다운로드는 **회차별로 행을 만들지 않고 시리즈당 1행**만 만들되, 시작일/
종료일은 이 계산 결과를 그대로 재사용해서 구한다:

- **시작일** = 남아있는(개별 취소/삭제되지 않은) 회차 중 가장 이른 시작일
- **종료일** = 남아있는 회차 중 가장 늦은 종료일

즉 중간 회차가 `ScheduleOccurrenceOverride`로 취소되면 시작일/종료일이 자동으로 그
다음/그 이전 남은 회차 기준으로 밀린다. **모든 회차가 취소된 경우, 해당 일정 자체를
다운로드 파일에서 제외**한다(더 이상 유효한 일정이 아니라고 판단).

회차별 개별 수정/취소 이력 자체(어떤 회차가 언제 바뀌었는지)는 컬럼으로 노출하지
않는다 — 시작일/종료일 계산에만 간접 반영된다.

## 4. 포맷별 처리 방침

- **CSV**: UTF-8 BOM 추가(한글 깨짐 방지), RFC 4180 방식으로 콤마/줄바꿈/따옴표
  포함 셀은 통째로 따옴표 처리(참조자 콤마-결합 셀 포함). 기존 라이브러리가 없어
  직접 구현하지만, 실제 난이도는 낮다고 판단(BOM + 이스케이프 함수 수준).
- **Excel**: `exceljs`(이미 설치됨, `^4.4.0`) 사용, `workbook.xlsx.writeBuffer()` —
  이 코드베이스에서 처음 쓰는 쓰기 경로이므로 날짜 셀 등 별도 검증 필요(참고:
  import 때 겪은 `t="d"` 버그 3종은 전부 읽기 전용 문제라 쓰기엔 직접 영향 없음,
  `taskImport.js` 참고).
- **HTML**: 스타일 없는 순수 `<table>` 마크업. 템플릿 엔진이 없어 문자열로 직접
  조립하므로, 제목/텍스트 등 사용자 입력값을 삽입할 때 `<`, `>`, `&`, `"`, `'`를
  반드시 HTML 엔티티로 이스케이프한다 — 빠뜨리면 다운로드한 파일을 열 때 삽입된
  스크립트가 그대로 실행되는 저장형 XSS가 된다. 표준적이고 간단한 처리이며,
  구현 체크리스트에서 빠뜨리지 않는 게 핵심이다.
- **JSON**: 스키마 방식으로 간다 — 최상위에 `schemaVersion`, `exportedAt`, `scope`
  같은 메타 필드를 두고, 레코드 필드명은 Prisma 필드명 기준으로 맞춘다(한글 라벨은
  CSV/Excel/HTML 전용). 참조자는 콤마 문자열이 아니라 배열.

## 5. 대용량 데이터 처리 — 우선순위 낮음, 구조만 마련

**2026-09-02 감사에서 수정**: 처음 구현 땐 이 차단을 "전체" 다운로드에만 걸어뒀는데,
scope=tasks/scope=schedules 단독 다운로드엔 건수 제한이 전혀 없어서 — 하필 "전체가
너무 크면 개별로 받으라"고 안내하는 그 대안 경로가 유일하게 무방비였다. 위험한 건
"한 응답 안에서 CPU 바운드로 만들어내는 총 행 수"이지 스코프 개수가 아니므로,
`EXPORT_ROW_LIMIT`(현재 2000) 하나를 **all/tasks/schedules 세 스코프 전부에 동일하게**
적용하도록 통일했다(`server/src/routes/projectExport.js`의 `estimateRowCount`).
판단은 **생성 시작 전에 건수만 먼저 세는 사전 차단 방식**을 쓴다(생성 도중 타임아웃
보다 안전).

같은 감사에서 "전체" 스코프의 건수 계산 자체도 버그였다는 게 드러났다 — 일감+일정
원본 건수만 더했는데, 실제로는 "일정" 파일에 날짜 있는 일감이 병합되어 두 번째로
포함되므로 실제 출력 행 수를 과소평가하고 있었다(§3.1). `countTaskRows`/
`countScheduleRows`(`projectExport.js`)로 통일해서 실제 출력 행 수를 정확히 추정하도록
고쳤다.

**차단 기준값(몇 건/몇 MB부터 막을지)은 아직 정하지 않았다** — 현재 운영 중인
프로젝트가 전부 테스트성 데이터라 판단 근거가 부족하다. 구조(건수 체크 → 기준
초과 시 차단)는 구현해뒀지만, 정확한 숫자는 실사용 데이터가 쌓인 뒤 따로 정한다.
전체 응답을 스트리밍 없이 메모리에 통째로 만드는 구조(CSV 문자열/xlsx 버퍼/zip
버퍼)는 그대로다 — 이 건수 제한이 사실상의 방어선이고, 사용 규모가 커지면 스트리밍
전환을 재검토해야 한다.

## 6. 구현에서 실제로 재사용한 기존 코드

- 일정 회차 계산: `server/src/lib/scheduleRecurrence.js`의 `expandOccurrences()`를
  `projectExport.js`의 `recurringRange()`에서 그대로 재사용 — 반복일정 시작/종료일
  계산과 "일감" 다운로드의 라벨 함수(`taskTypeLabel` 등, `server/src/lib/taskFields.js`에
  신규 추가) 둘 다 기존 코드를 손대지 않고 새 함수만 얹었다.
- 권한: `requireProjectRole('member')`(`server/src/lib/projectAccess.js`)를 그대로
  export 라우트에 적용 — 조회 권한과 동일하게 프로젝트 멤버 전원 허용.
- 파일 다운로드 응답 헤더 패턴(`Content-Disposition: attachment; filename*=UTF-8''...`):
  `server/src/routes/taskAttachments.js`의 패턴을 그대로 따름.
- zip 묶음: `jszip`(기존에 xlsx 셀 리라이트용으로만 쓰였음)을 새 라이브러리 추가 없이
  재사용.
- 프론트 다운로드 트리거: `src/lib/api.js`의 기존 `apiDownload()`를 그대로 사용하되,
  실패 시 서버의 한글 에러 메시지를 보여주도록 개선(413 안내 메시지가 이 경로로 뜬다).

## 7. 1차 범위에서 제외한 것

- 일감 `description`(마크다운 본문), 댓글, 첨부파일 실물, `TaskLink`
- 일정 회차별 개별 취소/수정 이력의 상세 노출(시작일/종료일 계산에만 간접 반영)
- 대용량 처리의 정확한 차단 기준값(구조는 만들되 숫자는 미정) — 현재 코드의
  `COMBINED_EXPORT_ROW_LIMIT`(2000)은 근거 없는 임시값, 실사용 데이터가 쌓이면 조정
- 시작일/종료일이 둘 다 없는 일감의 "일정" 스코프 포함(§3.1) — 화면의 placeholder는
  진짜 날짜가 아니므로 내보내지 않음
- 일감/진짜 일정을 구분하는 컬럼(§3, "구분" 컬럼안은 검토 후 기각)
- CSV 스킴은 처음엔 "구현 복잡하면 제외" 조건부였으나, 검토 결과 난이도가 낮아
  포함하는 것으로 확정됨

## 8. 구현 중 스펙에 명시 안 됐던 것 — 판단한 것

- **JSON에서 작성자/담당자/참조자**: "이름(이메일)" 합친 문자열이 아니라 `{name, email}`
  구조화 객체(참조자는 그 배열)로 만듦 — "스키마 방식" 요구에 더 맞는다고 판단.
  합친 문자열은 CSV/Excel/HTML에만 적용.
- **날짜 표현**: CSV/Excel/HTML은 전부 `YYYY-MM-DD` 문자열로 통일(실제 Date 셀
  아님) — exceljs 쓰기 경로가 처음이라 날짜 서식(numFmt) 리스크를 아예 없애는 쪽을
  택함. JSON은 Prisma가 내려주는 ISO 8601 문자열 그대로.
