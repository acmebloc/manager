# 일감 관계 스펙 (상위 / 하위 / 선행 / 후행 / 연결)

작성 2026-09-10. 업계 조사(Jira, Asana, Linear, ClickUp, Notion, Monday.com,
Azure DevOps, GitHub Issues)를 근거로 우리 서비스 규모에 맞춰 정한 내용이다.

## 0. 결정 요약과 근거

조사에서 확인한 업계 공통점은 세 가지였다.

1. **계층은 "부모 1개, 자식 다수"가 예외 없이 표준.** 우리는 이미 그렇게 되어 있다
   (`Task.parentTaskId`, 1단계만).
2. **거의 모든 툴이 "단순 연결"과 "순서·차단 관계"를 별도 타입으로 나눈다.**
   우리에게 없던 유일한 조각이 이것이고, 이번에 추가한다.
3. **계층과 차단을 섞으면 사고가 난다.** "부모-자식 간선을 차단 간선처럼 취급해서
   자식이 열려 있으면 부모를 시작조차 못 하게 막는" 버그가 실제로 보고돼 있다.
   그래서 이 스펙은 **계층과 선행 관계를 끝까지 분리**한다.

상태 전파 수위는 조사에서 두 모델로 갈렸다.

- **모델 A(Jira, Asana)** — 진행률만 보여주고 상태는 자동으로 바꾸지 않는다.
  자동화가 필요하면 사용자가 직접 규칙을 만든다.
- **모델 B(Linear)** — 팀 설정 토글 하나로 "하위 전부 완료 → 상위 자동 완료",
  "상위 완료 → 남은 하위 자동 완료" 양방향 전파.

**우리는 모델 A를 택한다.** 이유:

- 이미 검수 흐름(`docs/task-review-spec.md`)이 상태 전이를 엄격한 표로 통제하고
  있다. 여기에 계층 전파까지 얹으면 "왜 이 상태로 안 바뀌지"의 원인이 두 곳으로
  늘어나고, 전이표와 전파 규칙이 서로 충돌하는 경우를 매번 따져야 한다.
- 사용자가 이 기능에서 전파를 필수로 보지 않았고, 스펙 단순화를 반복해서 요구해
  왔다.
- 모델 A로도 실무의 핵심 질문("지금 뭘 못 하고 있나", "이 상위 일감은 얼마나
  됐나")에는 답할 수 있다. 그 답은 **표시**로 충분하다.

## 1. 관계 다섯 가지

| 관계 | 저장 위치 | 방향 | 개수 | 기능 연동 |
| --- | --- | --- | --- | --- |
| 상위 일감 | `Task.parentTaskId` | 자식 → 부모 | 부모 1개 | 진행률 표시 |
| 하위 작업 | 같은 필드의 역방향 | 부모 → 자식들 | 다수 | 진행률 표시 |
| 선행 일감 | `TaskLink(type='blocks')` | 선행 → 후행 | 다수 | 미완료 수 표시 |
| 후행 일감 | 같은 행의 역방향 | 후행 ← 선행 | 다수 | 없음 |
| 연결 일감 | `TaskLink(type='related')` | 대칭 | 다수 | 없음 |

다섯 관계 **모두** 일감 수정 화면에서 편집한다. 하위 작업과 후행 일감은 상대
일감이 가진 값을 바꾸는 것이라 저장 방식이 다르다(2장·5-1장).

`TaskLink.type`이 자유 문자열이고 유니크 제약이 `(fromTaskId, toTaskId, type)`이라
**마이그레이션 없이** `'blocks'`를 얹을 수 있다. `related`는 대칭이라 한 쌍당 한
행만 두고 양쪽에서 읽지만, `blocks`는 **방향이 의미를 갖는다** —
`{from: A, to: B}`는 "A가 B의 선행"이다.

## 2. 선행 / 후행 일감

용어는 **선행 / 후행**으로 한다. Azure DevOps의 Predecessor/Successor에 대응하고,
"차단"보다 업무 맥락에서 부드럽게 읽힌다.

- **선행·후행 둘 다 편집한다** (2026-09-11 변경).
  - 처음에는 후행을 읽기 전용으로 뒀다. 근거는 "양방향 편집을 다 열면 피커가 두
    개로 늘고, 같은 관계를 두 곳에서 지울 수 있어 헷갈린다"였다. **그런데 그 근거를
    하위 작업에는 적용하지 않았다** — 하위도 후행과 똑같이 "상대 일감이 나를
    가리키는" 역방향 관계인데 편집이 열려 있었다. 개념이 같으면 다루는 방식도
    같아야 하므로 후행을 열었다.
  - 후행 편집은 **상대 일감의 선행 목록**을 바꾸는 일이다. 그래서 목록 전체를
    덮어쓰는 `PATCH /:id { blockedByTaskIds }`를 쓰지 않고, 링크 한 개만 다루는
    `POST|DELETE /:id/blocked-by/:predecessorId`를 쓴다. 전체 교체로 보내면 내가
    편집하는 동안 다른 사람이 그 일감에 추가한 선행이 조용히 사라진다.
- **같은 프로젝트 안에서만.** 기존 연결 일감·계층과 같은 제약.
- **순환 금지.** A가 B의 선행이면서 B가 A의 선행이 될 수 없다. 간접 순환
  (A→B→C→A)도 막는다.
  - 근거: 순환이 생기면 서로 영원히 기다리는 상태가 되어 "미완료 선행 N개" 표시
    자체가 무의미해진다.
  - **검사와 쓰기 사이가 벌어지면 검사가 무의미해진다.** 읽고-검사하고-쓰는 사이에
    다른 요청이 끼어들면 둘 다 통과한 뒤 둘 다 써서 순환이 만들어진다(실측: 빈
    A/B에 `POST A/blocked-by/B`와 `POST B/blocked-by/A`를 동시에 보내면 둘 다
    204를 받고 순환 두 줄이 남았다). 그래서 후행 단건 경로는 프로젝트 단위
    advisory lock으로 직렬화한다 — 다른 프로젝트는 기다리지 않고, 락은 트랜잭션이
    끝나면 풀린다.
  - `PATCH /:id`의 선행 목록 교체에는 같은 경합이 남아 있다(이 작업 전부터 있던
    것). 거기까지 같은 락으로 감싸면 프로젝트 안의 일감 수정이 전부 직렬화돼서
    막으려는 문제보다 부하 영향이 크다. 만들어지는 상태도 되돌릴 수 없는 종류는
    아니다 — 제거 경로에는 순환 검사가 없어 화면에서 어느 쪽이든 지울 수 있다.
  - 새로 생기는 순환은 반드시 방금 저장한 일감을 지나가므로, 그 일감에서 후행
    방향으로 따라가 자신에게 돌아오는지만 검사하면 충분하다.
- **상태 전이를 막지 않는다.** 미완료 선행이 있어도 진행중·검수중으로 옮길 수
  있다. Jira와 ClickUp도 강제하지 않고 시각 신호만 준다 — 예외 상황이 실제로 있고,
  막아버리면 우회할 방법이 없다. 대신 아래 3장의 배지로 눈에 띄게 만든다.

## 3. 표시 (모델 A)

목록·보드에서 바로 보이는 것이 이 기능의 실질이다. 상세페이지에만 있으면 관계를
등록해도 아무도 눈치채지 못한다.

- **하위 작업 진행률** — `하위 2/5` 배지. 하위 작업이 없으면 배지 없음.
  - 이건 "칸반 카드/테이블 행에는 진행률 배지를 붙이지 않는다"는 이전 v1 결정
    (2026-09-07)을 **의도적으로 뒤집는 것**이다. 당시엔 무게가 걱정이었지만,
    `subtasks: { select: { status: true } }`는 이미 같은 자리에 있는
    `checklistItems: { select: { done: true } }`와 같은 비용이다.
- **미완료 선행 수** — `선행 대기 2` 배지. 완료되지 않은 선행 일감이 있을 때만.
- 두 값은 서버가 조인해서 내려주고, 개수 계산은 체크리스트 배지와 같은 방식으로
  클라이언트가 한다. 목록 조회에 붙는 SQL은 일감 수와 무관하게 3개
  (하위 작업 / 링크 / 링크 상대 일감)로 고정이다 — 실측으로 확인했다.
- **두 배지는 다른 일감의 완료 여부에 달려 있다.** 그래서 완료 경계를 넘는 상태
  변경(→완료, 완료→)은 방금 옮긴 카드만 갱신해서는 부족하고, 목록을 다시 읽는다.
  대기↔진행중처럼 배지에 영향이 없는 전이는 낙관적 업데이트로만 끝낸다 — 드래그
  한 번마다 전체 재조회가 일어나면 그게 더 큰 비용이다.

## 3-1. 피커 후보에서 빼는 것

- 선행 후보에서 **후행 일감**을, 후행 후보에서 **선행 일감**을 뺀다. 한 쌍을
  양방향으로 걸면 곧바로 순환이라 서버가 거절하므로, 애초에 고를 수 없게 하는
  쪽이 저장 후 에러를 보는 것보다 낫다. 간접 순환(A→B→C→A)은 서버만 잡을 수 있다.

- **연결 일감은 나머지 네 관계와 양방향 배타다** (2026-09-11 변경).
  연결 후보에서 상위·하위·선행·후행을 모두 빼고, 반대로 연결로 이어진 일감은
  상위·하위·선행·후행으로도 걸 수 없다.
  - 근거: 연결은 "순서도 계층도 아닌 그냥 관련"이라는 가장 약한 관계다. 더 구체적인
    관계가 이미 있으면 연결을 덧붙여도 정보가 늘지 않고, 상세 화면 한 상자에 같은
    제목이 두 번 뜨고 관계도에는 선이 겹친다.
  - 처음에는 (가) 계층을 제외 목록에서 빠뜨렸고 (나) 반대 방향을 일부러 열어뒀다
    ("연결로 걸어둔 일감을 나중에 선행으로 올리는 건 관계를 구체화하는 것"). 그런데
    그 경로로 들어가면 결국 같은 중복이 만들어진다. 지금은 양방향으로 막고, 바꾸고
    싶으면 연결을 먼저 지우게 한다.
  - **서버에서 강제한다**(`server/src/lib/taskRelationRules.js`). 화면 제외만으로는
    부족하다 — 실제로 이 검증을 넣기 전에는 선행으로 걸린 일감을 API로 연결에도
    걸 수 있었다(화면은 막고 있었는데도).

- **상위와 선행은 같은 상대에게 함께 걸 수 있다.** 뜻이 다르기 때문이다(상위=포함,
  선행=순서). 관계도에서 두 선을 서로 다른 높이에 그린다(6장).

## 4. 하지 않는 것 (명시적 제외)

- **상태 자동 전파** — 하위가 전부 완료돼도 상위 상태는 그대로. 상위를 완료해도
  하위는 그대로. (1장 근거 참고)
- **상태 전이 차단** — 미완료 선행이 있어도 막지 않는다.
- **관계 변경 활동 로그** — 연결 일감이 지금 로그를 남기지 않는 것과 같은 기준.
  상위 일감 변경만 예외적으로 남는다(필드 변경이라서).
- **내보내기·검색·엑셀 일괄등록에 관계 포함** — 내보내기는 1차 범위에서 관계를
  뺐고(`docs/project-export-spec.md`), 그 결정을 유지한다. 엑셀 일괄등록도
  관계 열을 두지 않는다: 관계는 다른 일감의 id를 가리키는 값이라 등록 시점에는
  아직 존재하지 않는 행을 참조해야 하는 경우가 생긴다(같은 파일의 뒷줄).
  등록 후 일감 화면에서 잇는 쪽이 맞다.
(관계도 시각화는 이 목록에 있었으나 2026-09-10에 만들었다 — 6장 참고.)

## 5. 완료 잠금과의 관계

완료된 일감은 필드가 잠긴다(`docs/task-review-spec.md` 8장). 선행 일감 목록도
그 일감의 필드로 취급해 **완료 상태에서는 바꿀 수 없다**(`EDITABLE_FIELD_KEYS`에
포함). 연결 일감·상위 일감과 같은 취급이다.

단, 하위 작업·후행 일감은 **상대 일감**을 고치는 것이라 잠금도 상대 기준이다 —
이쪽 일감이 완료여도 상대가 완료가 아니면 통하고, 반대로 상대가 완료면 이쪽이
진행중이어도 막힌다(409).

그래서 **완료된 일감은 하위 작업·후행 일감 후보에서 빼고, 이미 걸려 있으면 제거
버튼을 비활성**으로 둔다(이유는 버튼에 붙인다). 다섯 관계가 모두 draft가 되면서
저장 한 번에 여러 요청이 순서대로 나가는데, 완료된 하위를 제거하는 요청이 가장
먼저 나가므로 거기서 막히면 **제목 수정조차 서버에 닿지 못한다.** 선행·연결·상위는
내 필드라 이 제약이 없다.

## 5-1. 저장 모델 — 다섯 관계 모두 draft (2026-09-11)

**관계 다섯 가지는 전부 저장 버튼을 눌러야 반영된다.** 그전에는 상위·선행·연결만
draft였고 하위 작업은 즉시 PATCH였다. 그래서 같은 상자 안에서 어떤 관계는 취소가
통하고 어떤 관계는 안 통했고, 더 나쁘게는 이런 일이 났다:

    수정모드에서 상위를 제거 → 화면에서는 사라짐(draft) → 하위를 추가
    → 서버는 아직 옛 상위를 보고 400 거절

**즉시 저장으로 통일하는 대신 draft로 통일했다.** 즉시 저장이면 "전체 취소"가
되돌리는 요청을 여러 개 보내야 하는데, 원자적이지 않아 절반만 되돌아갈 수 있고,
그 사이 남이 바꾼 관계를 덮어쓰고, 상대가 완료되면 되돌릴 수 없고
(`EDITABLE_FIELD_KEYS` 잠금), `parentTaskId`가 활동 로그 추적 대상이라
"바꿨다가 되돌린" 흔적이 로그에 남는다.

하위 작업과 후행 일감은 상대 일감을 고쳐야 하므로 저장할 때 상대마다 요청을
따로 보낸다. **순서가 중요하다 — 제거를 먼저, 추가를 나중에:**

    1. 하위 제거   PATCH 상대 { parentTaskId: null }
    2. 후행 제거   DELETE 상대/blocked-by/나
    3. 내 필드     PATCH 나 { parentTaskId, relatedTaskIds, blockedByTaskIds }
    4. 하위 추가   PATCH 상대 { parentTaskId: 나 }
    5. 후행 추가   POST 상대/blocked-by/나

계층이 1단계뿐이라(`assertValidParent`) 순서를 뒤집으면 정당한 편집도 거절된다.
*상위 A를 지우고 하위 B를 추가*는 3번이 내 상위를 비운 뒤 4번이 B를 붙여야
통하고, *하위 B를 지우고 상위 A를 등록*은 1번이 B를 떼어낸 뒤 3번이 붙여야 통한다.

**상위와 하위는 서로를 비활성시킨다.** 상위가 있으면 하위 피커를, 하위가 있으면
상위 피커를 비활성으로 두고 이유를 placeholder에 적는다. 입력창을 숨기지 않는
이유는 숨기면 기능이 없는 줄 알기 때문이다. 판단은 draft 기준이라 화면과 서버가
어긋날 수 없다 — 위의 400 문제가 구조적으로 사라진다.

**이 요청들은 한 트랜잭션이 아니다.** 중간에 실패하면 앞의 요청은 이미 반영된 채
멈춘다. 그래서 실패했을 때 (가) 몇 개가 반영됐는지 세어 하나라도 반영됐으면 서버
상태를 다시 읽어오고, (나) 실패한 요청이 어느 일감의 어느 관계였는지를 메시지
앞에 붙인다. 둘 다 실측으로 필요성이 확인됐다:

- 하위 하나를 제거하고 완료된 일감을 하위로 추가하면 제거는 반영되고 추가만
  409였는데, 화면은 제거 전 목록을 그대로 보여줬고 취소를 눌러도 서버엔 없는
  하위가 다시 나타났다.
- 완료 잠금·권한 거절은 **상대 일감** 때문에 나는데 서버 메시지만 그대로 띄우면
  지금 편집하던 일감이 잠긴 것처럼 읽혔다.

**신규 등록은 관계 실패와 무관하게 상세로 넘어간다.** POST가 성공한 뒤 관계
요청이 실패해도 일감은 이미 만들어졌기 때문이다. 등록 화면에 머물면 사용자가
저장을 다시 눌러 **같은 일감이 한 번 더 만들어진다**(실측). 상세로 옮기고
무엇이 안 됐는지만 알린다.

**쓰기 응답에는 하위 작업의 제목이 없다.** POST/PATCH는 목록·보드와 같은
include를 쓰고(`taskWriteInclude` → `taskInclude`) 거기서 `subtasks`는 진행률
배지용 `{ status }`만 뽑는다. 제목까지 실린 형태는 `GET /:id`에서만 온다. 그래서
쓰기 응답으로 화면 state를 갈아끼울 때는 하위 작업 목록을 지금 들고 있는 것으로
지켜야 한다(`withSubtasks`). 안 지켰을 때: 상세에서 상태만 바꿔도 하위 작업 칩이
제목과 링크를 잃었고, 그 칩을 제거하면 id가 `undefined`라 목록이 통째로 지워졌다.

## 6. 관계도 뷰 (2026-09-10 추가)

일감 페이지의 세 번째 뷰 모드다: **보드 / 목록 / 관계도**. 별도 메뉴를 만들지
않은 이유는 보는 대상(한 프로젝트의 일감들)이 같기 때문이다 — 같은 데이터를
다르게 볼 뿐이라 뷰 토글이 맞다.

- 화면 상단에서 프로젝트를 하나 고른다(일정 화면과 같은 `ProjectPicker`,
  기본값은 가장 최근 프로젝트). 관계는 프로젝트 안에서만 맺어지므로 그래프도
  프로젝트 단위다. 선택은 `?projectId=`로 URL에 남아 새로고침·공유에도 남는다.
- 전용 엔드포인트 `GET /api/projects/:projectId/tasks/relations`가 일감
  4개 필드(id·제목·상태·상위)와 링크 3개 필드만 내려준다. 목록용
  `taskInclude`를 재사용하지 않는 이유는 그래프에 담당자·첨부·댓글 수가
  필요 없어서다 — 쿼리는 2개(일감·링크) 고정이다.
  - **이 라우트는 `GET /:id`보다 위에 있어야 한다.** 아래로 내려가면
    `relations`가 `:id`로 잡혀 404가 난다. 소스에도 같은 주석을 달아뒀다.

### 그리는 방식

- **좌→우 계층 배치(dagre, `rankdir: 'LR'`)**. 선행/후행에서 사용자가 묻는 건
  "무엇을 먼저 해야 하나"인데, force-directed(물리 기반 산개) 배치는 그 답을
  위치로 주지 못한다 — 열 때마다 배치가 달라져 화살표를 하나씩 따라가야 한다.
  좌→우로 놓으면 위치 자체가 순서다.
- 관계 종류는 **선 모양**으로만 구분한다(선행=실선 화살표, 계층=파선,
  연결=점선). 색까지 다르게 하면 노드 테두리의 상태 색과 경쟁한다. 범례는 따로
  띄우지 않고 필터 체크박스에 선 견본을 붙였다 — 켜고 끄는 자리에서 바로 보인다.
- 노드에 마우스를 올리면 직접 이어진 것만 남기고 나머지를 흐리게 한다. 노드를
  클릭하면 그 일감 상세로 간다.
- 기본 필터: **완료 숨기기 켜짐, 관계 없는 일감 숨김.** 관계도를 열었을 때 무관한
  덩어리부터 보이면 안 되기 때문이다. 양쪽 끝이 다 보이는 관계만 선을 그린다 —
  한쪽이 필터로 빠졌는데 선만 남으면 어디로 가는 선인지 알 수 없다.

### 규모를 견디는 방법

- **뷰포트 컬링** — 노드가 100개를 넘으면 `onlyRenderVisibleElements`를 켜서
  화면 밖 노드는 그리지 않고, 화면을 옮기면 그때 그린다. 항상 켜지 않는 이유는
  React Flow 문서가 명시하듯 이 최적화 자체에 오버헤드가 있어서다.
  (168노드로 실측: 확대 시 DOM 노드 88개, 패닝하면 36개가 새로 생겼다.)
- **노드 크기를 상수로 고정**해 React Flow에 직접 넘긴다. 크기를 안 주면
  DOM을 재기 전까지 "크기 없음" 상태라 미니맵에 아무것도 안 그려진다.
- **`minZoom`을 0.05로 낮췄다.** 기본값 0.5로는 일감 수십 개만 넘어도 "전체
  보기"가 화면에 안 들어와 그래프가 잘린 채 열린다.
- 배치 계산(dagre)은 데이터·필터에만 의존하게 분리했다. hover 흐리기와 한
  묶음이면 마우스가 노드를 스칠 때마다 그래프 전체를 다시 배치하게 된다.
- 화면 전체를 `lazy()`로 분리했다 — React Flow와 dagre(약 264 kB)는 관계도를
  열 때만 받는다.
